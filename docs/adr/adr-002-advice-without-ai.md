# ADR-002: Разбор проблем — словари и эвристики, без внешнего ИИ

Дата: 2026-11-02. Статус: принято. Источник: spec R03, manifest R02/R03 («его отмена» — решение пользователя).

## Контекст

Требование R03 — «качественный разбор проблем сайта», но на брифинге пользователь отменил подключение реального ИИ-провайдера. Старый разбор был rule-based демо-уровня и не покрывал объяснения security-находок и план действий. Разбор нужен оффлайн и одинаковым на всех трёх поверхностях.

## Решение

Разбор строится на рукописных словарях и эвристиках в `engine/advice/`: `RULE_TIPS` (~40 правил axe), `tipFor`, `whyForRule`/`whyForSecurity` («почему это проблема — человеку») для каждого правила axe и каждой sec-проверки; `buildAdvice` — движки express/deep/strict (`ENGINE_OPTIONS`) меняют только объём текста совета, сами проверки axe всегда одинаковые. Сверх объяснений: `buildRemediationPlan` — план исправления по убыванию эффекта с оценкой усилия (минуты/часы/дни, `EFFORT_LABELS`) и `simulateScores(result, fixedIds)` — симуляция «если исправите» без пересканирования. Всё — чистые функции над данными, покрываются юнит-тестами на фикстурах.

## Последствия

- Детерминированно, оффлайн, без ключей и расходов; пользователь получает план и пересчёт скоров «на лету» — то, для чего обычно зовут LLM.
- Объяснение одно и то же в вебе, CLI и PDF — расхождений в совете быть не может.
- Цена: покрытие ограничено словарём — неизвестное правило axe получает fallback-текст, каждое новое правило требует ручной записи в оба словаря (советы + «почему»); качество объяснений ограничено тем, что написано руками, и само не растёт; «AI-помощник» в UI остаётся rule-based и названия «ИИ» не заслуживает.
