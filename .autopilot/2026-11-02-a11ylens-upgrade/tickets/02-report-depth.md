## Что должно заработать

Скан исследует до 4 страниц (главная + первые внутренние ссылки), нарушения группируются по страницам. Каждая находка безопасности несёт доказательство (evidence). В отчёте — словарь «почему это проблема — человеку» для каждого правила и находки, раздел «План исправления» с приоритетами и оценкой усилия, и симуляция «если исправите»: чекбокс у находки пересчитывает оба скорa. Пустой результат — «чисто»-состояние, недоступный сайт — ошибка с причиной (DNS/TLS/404/таймаут) и что проверить.

## Из брифа, дословно

> «и исследований ошибок сайта»
> «сделай более качественный разбор проблем сайта»
> Дополнение: «по вопросу 3 (ИИ-провайдер): реальный ИИ не подключаем вообще; разбор проблем углубляется без внешнего ИИ»

## Разделы спецификации

Истории 6–13 (R02, R02.1–R02.3, R03, R03.1–R03.3), Решения §движок/скоринг.

## Критерии приёмки

- [ ] скан обходит до 4 страниц; в отчёте видно, какие страницы просканированы и на какой найдено каждое нарушение; лимит настраивается
- [ ] у каждой SecurityFinding заполнен `evidence` — конкретный заголовок/куки/фрагмент; находка без evidence не показывается как сработавшая
- [ ] у каждого нарушения и находки — абзац объяснения по-человечески (почему проблема, кого задевает)
- [ ] раздел «План исправления»: действия по убыванию эффекта на скор, с оценкой усилия (минуты/часы/дни); для непустого отчёта ≥3 шага
- [ ] чекбокс «исправлено» у находки пересчитывает скоры доступности и безопасности без пересканирования; ручной пересчёт по весам сходится
- [ ] сайт с 0 нарушений показывает «чисто»-состояние с подсказками, что делать дальше; недоступный сайт — ошибка с классификацией причины
- [ ] `npm test` зелёный (новая логика покрыта), `npm run build` проходит, localStorage-ключи истории не меняются
